   Ese es el formato que permite el emparejamiento. El comando con el que se
   hizo, sobre la salida completa del bloque:

      adb shell dumpsys backup \
        | sed -n '/BACKUP MANAGER MONITOR EVENTS/,/END OF BACKUP/p' \
        | python3 - <<'FIN'
import sys, re, collections
ev = None; pares = []
for l in sys.stdin:
    m = re.match(r"\[([\d\- :.]+)\] - (.+)", l.strip())
    if m: ev = (m.group(1), m.group(2)); continue
    m2 = re.match(r"Package: (\S+)", l.strip())
    if m2 and ev: pares.append((ev[0], ev[1], m2.group(1))); ev = None
aur = [p for p in pares if p[2] == "com.auroraclima.app"]
print(len(pares), len(aur), collections.Counter(e for _, e, _ in aur))
FIN

[3] PORTAPAPELES — MASWE-0030                               (2026-10-10)

   La evidencia SÓLIDA de este control es estática: la app no usa el
   portapapeles en ninguna parte.

$ grep -rnE 'ClipboardManager|ClipData|setPrimaryClip|LocalClipboardManager' --include='*.kt' app/src/main
   [sin resultados: cero ocurrencias en todo el código de la app]

   Lo dinámico NO se pudo establecer, y conviene dejarlo claro porque una
   primera versión de esta evidencia lo interpretó mal:

   · «adb shell dumpsys clipboard» devuelve SALIDA VACÍA con código 0. No hay
     forma de saber si eso significa «el portapapeles está vacío» o «este dump
     no imprime nada en este build»: no existe «cmd clipboard» («No shell
     command implementation») para poner un valor de control y comparar.

   · «adb shell service call clipboard 1» NO LEE el portapapeles. La
     transacción 1 de IClipboard en API 35 es setPrimaryClip, es decir una
     ESCRITURA. El Parcel que devuelve empieza con 0xfffffffd (= -3,
     EX_ILLEGAL_ARGUMENT) y la cadena «No items», y a continuación trae 912
     bytes de traza que lo delatan:

        at com.android.server.clipboard.ClipboardService$ClipboardImpl
             .checkAndSetPrimaryClip(ClipboardService.java:584)
        at com.android.server.clipboard.ClipboardService$ClipboardImpl
             .setPrimaryClip(ClipboardService.java:513)
        at android.content.IClipboard$Stub.onTransact(IClipboard.java:191)

     «No items» es el mensaje de la IllegalArgumentException que lanza el
     servicio porque el ClipData que la propia sonda le pasó venía vacío. No
     dice NADA sobre el contenido del portapapeles.

   Conclusión que sí se sostiene: Aurora nunca escribe en el portapapeles
   (grep de arriba), y los campos de clave y contraseña usan
   PasswordVisualTransformation, que desactiva «copiar» en la barra de
   selección. Lo que queda sin medir es si la usuaria, copiando a mano desde
   el campo de relato, deja el texto expuesto; está declarado como observación
   en el informe y como limitación 4.3.4.
